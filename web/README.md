# TamaPoke web installer

A one-click page that flashes the firmware and loads the sprites from the browser
(Chrome/Edge), with no Arduino or drivers. It uses
[ESP Web Tools](https://esphome.github.io/esp-web-tools/) to flash (a pinned copy
in `vendor/`, see *Third-party code* below) and **Web Serial** to push the sprites
to the SD with the firmware's `PUT` protocol (the same one as `tools/send_sd.py`).

## Contents

- `index.html` — the installer and board-manager shell.
- `style.css` / `installer.js` — responsive UI, Web Serial transport, pack
   reconciliation, and save backup/restore.
- `savefile.js` / `packs.js` — the save format and the pack upload protocol. Neither
   may touch `window`, `document` or `navigator`, so `node` can test them:
   `tools/check_savefile.mjs` and `tools/check_packs.mjs`.
- `editions.json` — the GitHub repository queried for Releases plus the fallback
   description for the current Pages build.
- `manifest.json` — the current build's ESP Web Tools config.
- `paks.json` — generated region sizes, CRC32s, file counts, and firmware region
   indices.
- `dex.json` — species names and the level rule, generated by
   `tools/gen_web_dex.py` from the game's own data, for backup labels.
- `vendor/esp-web-tools-<version>/` and `fonts/` — third-party code and fonts,
   served from here rather than from a CDN.
- `firmware/bootloader.bin` `partitions.bin` `boot_app0.bin` `app.bin` — what the
  installer actually writes, each at its own offset. **This is deliberate**: a
  single image at `0x0` pads the gaps with `0xFF` and so blanks the NVS
  partition at `0x9000`, which is the player's save. `tools/check_installer.py`
  fails the build if anything the manifest ships would land on it.
- `firmware/tamapoke.bin` — the same four merged into one image for flashing a
  **blank** board from the command line. Not in the manifest, because installing
  it over an existing game erases the pet.
- `sprites-<region>.pak` — the sprites bundled (TPAK) **one file per region**, so
   the page sends a region in one click. They are **generated** by
  `tools/pack_bundle.py`, which derives the region list from `dex_data.py`, and
  **committed** — see *Hosting the sprites* below for why they have to be.

## Regenerate

After changing the firmware or the sprites:

```bash
bash tools/build_web.sh        # recompiles -> firmware/, dex.json, the JS cache keys, AND the region .paks
```

## Test locally

Web Serial and ESP Web Tools need a **secure context**: `https://` or
`http://localhost`. Serve the **repository root**, not `web/`: the page reads
`../docs/` for its screenshots and release notes.

```bash
python3 -m http.server 8000
# open http://localhost:8000/web/ in Chrome/Edge
```

## End-user flow

1. Pick a firmware version. On a board that already has a game, press **Back up
   save** first, then **Install firmware**; a new board can go straight to Install.
   Pick the USB port, and only tick "Erase device" for a fresh board. When the
   page knows the board runs a NEWER version than the one picked (firmware after
   v3.25 reports it), Install waits for a backup of that board, since older
   firmware may not read a newer save in full.
2. **Connect board**. The page asks the board who it is (its ID and, after v3.25,
   its version), then compares the installed SD marker for every region against
   the CRC in `paks.json` and labels it Current, Update available, Installed /
   unversioned, or Not installed. A board that does not answer at all is released
   straight away with a pointer to step 1, instead of after half a minute of
   timeouts. After a firmware install the page finds the board again by itself
   once the install dialog is closed, if it is the only one attached.
3. **Select needed** excludes current packs. Install the remaining choices over
   USB. Progress is by bytes across the whole install, with the time left measured
   from the board's actual rate: about 6 minutes per 40 MB on v3.25 firmware, and
   roughly two and a half times that on older firmware. The next pack downloads
   while the current one is sent. On firmware after v3.25 every file is read back
   off the card and compared, and a file the card already holds is skipped, so an
   interrupted install resumes and an update sends only what changed. A failure
   says why next to the progress bar and offers Retry. While files arrive the
   board shows a transfer screen and pauses the game, which comes back by itself a
   few seconds after the last file.
4. **Download save** and **Back up save** both verify the save before offering it.
   **Restore save** accepts that same `.tpsave`, first keeps a copy of the save it
   is about to replace in *Recent backups*, says if the backup came from a
   different board, streams the `IMPORT` commands with flow control, and lets the
   firmware validate the whole checksum before NVS is changed. The page reconnects
   by itself when the board has restarted.
5. Firmware v3.25 and older loads the Pokedex thumbnails only at boot, so restart
   it after changing packs; later firmware reloads them by itself.

If the board reports no usable microSD card, the page asks it to mount the card
again (which also finds one inserted after boot). If the card still cannot be read,
as with most cards over 32 GB, which are sold as exFAT, **Format card** offers to
format it, after a confirmation. The firmware no longer formats a card unasked.

The page keeps a screen wake lock and warns before closing while a job runs, and
**Copy diagnostics** in the activity log gathers what a bug report needs.

The custom-file option lets advanced users send their own `.bin`. Because those
files did not come from a known bundle, the page clears every pack marker first,
so every region reports as unversioned until it is installed again.

## Firmware versions and GitHub Releases

The version selector queries the public GitHub Releases API for the repository
named in `editions.json`. A Release supplies the version name, date, channel,
link, and changelog body. The bytes do not come from Release attachments:
GitHub's attachment downloads have no browser CORS header. Instead, each option
uses the immutable `web/manifest.json` and four firmware parts committed at that
Release's tag through `raw.githubusercontent.com`, which does allow browser
fetches.

The page validates a release before showing it. Its tag must match the manifest
version, `new_install_prompt_erase` must be true, and the ESP32-S3 build must
contain exactly the four safe offsets. Drafts and invalid tags stay invisible.
If GitHub is unavailable, or no releases exist yet, the current Pages manifest
remains available as a fallback. Its changelog is then read from
`docs/release-notes/v<version>.md` on this same site, so the page does not need
the GitHub API (60 requests an hour per address, unauthenticated) to show it.

To publish a version -- the full rules, and why, are in `CLAUDE.md` § Releasing
and § Git:

1. On a feature branch, set `FW_VERSION` in `TamaPoke.ino` and the README
   firmware badge to the same version, and write
   `docs/release-notes/vX.Y.md` for players.
2. Run `bash tools/build_web.sh` **after the last source edit**; this compiles the
   exact firmware, updates the manifest, `dex.json` and every cache key, and
   checks that NVS is outside the write ranges.
3. Run `python3 tools/check_release.py vX.Y`. It also rejects stale firmware
   hashes, a missing or thin changelog, failing web tests, or any disagreement
   among the tag, source, README, and manifest.
4. Commit, push the branch, merge it into `main` and push `main`. Only then tag
   the merged commit:

   ```bash
   git tag -a vX.Y -m "TamaPoke vX.Y"
   git push origin vX.Y
   ```

The `publish-release.yml` action validates the tag again (including that it is on
`main`), creates the GitHub Release, and publishes `docs/release-notes/vX.Y.md`
as its changelog, which is what the page shows. The Pages selector discovers it
automatically; no HTML or catalogue edit is needed for later releases.

## Installed pack identity

`paks.json` carries the CRC32 of each complete TPAK. The browser verifies that
download before sending any file, then uses these firmware commands:

```text
PACKS                         # PACK <region-index> <crc|legacy|missing>
PACK BEGIN <region-index>     # remove the old marker before changing files
SUM <path>                    # SUM <crc32> <bytes> of the file as stored (after v3.25)
PACK COMMIT <index> <crc32>   # write it only after all PUTs and probes pass
SD MOUNT [FORMAT]             # mount a card; FORMAT one it cannot read (after v3.25)
```

An interrupted upload therefore cannot continue to claim that the old version
is current. `PUT` also checks the SD write length and invalidates the relevant
marker itself, so `tools/send_sd.py` and manual uploads cannot leave a false
Current status behind. Cards populated before this protocol are detected by the
existing start/middle/end probes and shown as Installed / unversioned once;
reinstalling writes the exact version marker.

`SUM` is what makes "installed and verified" describe the card rather than the
download: the page compares every file it sends with the CRC32 the board reads
back, since a failing or counterfeit card accepts every write. The same check,
before sending, skips a file the card already holds byte for byte. The page
probes for it with a file that cannot exist, which newer firmware answers with
`ERR` at once and older firmware ignores, so no real file waits out a timeout.

Every regional bundle includes the same shared `thumbs.bin`. During a managed
`PACK BEGIN` transaction, replacing that file invalidates only the region being
installed; a standalone custom upload still invalidates all markers. The page
also remembers exact hashes it verified during the current session and repairs
those markers after a successful batch, which preserves correct status when
installing several regions through older v3.16 firmware.

Because of that shared file, adding a region changes EVERY pack's CRC while not
one of their sprites changes. `pack_bundle.py` therefore compares each rebuilt
pack with the one it replaces and, when every region file is byte-identical and
the region's own thumbnails are too, records the old CRC under `equivalent` in
`paks.json`. A card carrying an equivalent marker is shown as Current. Without
this, the Galar and Paldea packs would have asked every player to re-send the
other seven regions -- about 230 MB -- to change nothing on screen.

## Hosting the sprites

**The `.pak` files ARE committed, and that is deliberate.** They have to be
served **same-origin** from GitHub Pages, because **GitHub release assets send
no CORS headers at all** — a browser `fetch()` of one is blocked, however much
nicer it would be to keep ~285 MiB out of the repo. Verified with an `Origin`
header: the asset returns `200` and no `access-control-allow-origin`, while
Pages sends `access-control-allow-origin: *`.

This page said the opposite for a long time — "gitignored", "not committed",
"serves Access-Control-Allow-Origin" — while `.gitignore` carried the real
reason and the files were tracked. Acting on this file rather than on the code
untracks them and silently breaks every download button. It is written down
here now so the next person does not have to find out the same way.

```bash
bash tools/build_web.sh   # rebuilds the firmware, the manifest and every .pak
git add web/sprites-*.pak # yes, really
```

The page fetches the packs from the same directory as `index.html`, each keyed by
its own CRC (`sprites-<region>.pak?v=<crc32>`), the way the firmware parts and
scripts are keyed by theirs: Pages lets a browser keep a file for 10 minutes, and
a cached old pack right after a release fails its checksum. Same-origin is the
path that works in a browser and keeps CRC metadata beside the exact bytes it
describes.

**Why one file per region and not one big one:** all nine together come to about
285 MiB, and GitHub's hard per-file limit is 100 MB — a single bundle would be
uncommittable. Splitting also means most people can take Kanto (~40 MB) and
stop, and add a region later without re-sending what is already on the card.
A region whose `.pak` is not on the card shows as locked in the Pokedex chooser
and is kept out of the egg pool, so a partial install is a supported state
rather than a broken one.

All sprites are from PMD SpriteCollab, CC BY-NC (non-commercial sharing with
attribution is allowed); see [`../CREDITS.md`](../CREDITS.md).

## Third-party code

**esp-web-tools is vendored, and pinned by its folder name.** Whether an update
keeps the player's save comes down to one line in ITS install dialog --
`new_install_prompt_erase ? ASK_ERASE : _startInstall(true)`, with the Erase box
unchecked -- and the page used to load it from a floating `unpkg.com/...@10` tag,
which served whatever 10.x was newest. `tools/check_installer.py` now reads the
vendored copy: it refuses a CDN script, a folder whose `package.json` disagrees
with its name, a relative import with no file behind it, a file Jekyll would not
publish (a leading `_` or `.`), and any dialog where the flag no longer means
"ask" or the box starts checked.

To move to a newer esp-web-tools, unpack its npm tarball, copy `dist/web/*.js`,
`LICENSE` and `package.json` into `web/vendor/esp-web-tools-<version>/`, point the
`<script>` in `index.html` at it, delete the old folder, and run
`python3 tools/check_installer.py`. Then flash a board that has a save and check
that it survives: the check reads the code, not the behaviour.

The two fonts (DM Sans and Azeret Mono, SIL OFL 1.1, licences beside them) live in
`fonts/` rather than on Google Fonts, which saw the address of every visitor.

## Deploy (GitHub Pages)

1. Repo settings → Pages → deploy from a branch: `main`, folder `/ (root)`. A
   branch can only be served from `/` or `/docs`, and the page needs the root:
   it reads `../docs/screens/` and `../docs/release-notes/`. Pages gives HTTPS
   automatically.
2. The installer is then at `https://<user>.github.io/<repo>/web/`.

> **Pages on private repos** needs GitHub Pro/Team. If you make the repo
> **public** to use Pages for free, decide about the sprites first (see above and
> CREDITS).

## Limitations

- Desktop **Chrome/Edge** only (Web Serial isn't in Firefox/Safari).
- Firmware from before the `PACKS` protocol can still receive packs and use save
   backup/restore, but the page cannot identify exact installed pack versions.
   Flash the current firmware once to enable comparison.
- Firmware up to v3.25 does not report its version, read files back (`SUM`),
   mount a card after boot or reload thumbnails by itself. The page still
   installs packs and restores saves on it, and says what it cannot check.
